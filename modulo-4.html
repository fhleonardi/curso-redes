1. Qué agrega la capa de transporte

IP lleva paquetes de un host a otro. Pero en un host corren muchos programas a la vez: el navegador, el cliente de correo, un servidor web. La capa de transporte entrega cada dato al proceso correcto, y para eso usa puertos: números de 16 bits (0 a 65535) en la cabecera TCP o UDP.

Socket y conexión

Un socket es la interfaz que ofrece el sistema operativo para que un programa use la red. Una conexión TCP queda identificada por cuatro datos: IP y puerto de origen, IP y puerto de destino.

Cliente 192.168.1.20:53124  ───── TCP ─────►  Servidor 203.0.113.10:443
        (puerto efímero)                              (puerto conocido)

Por eso un servidor web puede atender a miles de clientes en el mismo puerto 443: cada conexión se distingue por la IP y el puerto del cliente.

No confundir

El puerto lógico (un número en la cabecera TCP o UDP) no tiene nada que ver con el puerto físico de un switch, donde se enchufa el cable.

2. UDP

UDP agrega lo mínimo sobre IP: puertos, largo y una suma de verificación, en 8 bytes de cabecera. No abre conexión, no confirma, no reordena ni retransmite. Si un datagrama se pierde, UDP no hace nada.

Se elige UDP cuando:

  • importa más llegar a tiempo que llegar completo: voz, video en vivo, juegos;
  • los mensajes son cortos y la aplicación puede reintentar: DNS, DHCP, NTP;
  • se necesita broadcast o multicast, que TCP no admite;
  • la aplicación prefiere implementar su propia confiabilidad: QUIC, el transporte de HTTP/3.

3. TCP

TCP ofrece un flujo de bytes confiable, ordenado y bidireccional entre dos procesos. Sus mecanismos:

Establecimiento en tres pasos

Cliente                                Servidor (LISTEN)
  │── SYN       seq=x ─────────────────►│
  │◄─ SYN-ACK   seq=y  ack=x+1 ─────────│
  │── ACK       ack=y+1 ───────────────►│
          ESTABLISHED en ambos extremos

En el establecimiento cada extremo elige su número de secuencia inicial al azar, confirma el del otro y anuncia su MSS y su ventana. Si nadie escucha en el puerto, el servidor responde RST, y el cliente informa «conexión rechazada». Si no responde nadie, el cliente reintenta el SYN y termina por agotar el tiempo.

Secuencia, confirmación y retransmisión

El número de secuencia indica qué byte del flujo lleva cada segmento. El ACK indica el próximo byte que el receptor espera, y así confirma todo lo anterior. Si un segmento no se confirma a tiempo, o llegan tres ACK duplicados, TCP lo retransmite.

Control de flujo y de congestión

  • Control de flujo: el receptor anuncia cuántos bytes puede aceptar (ventana de recepción). Protege al receptor.
  • Control de congestión: el emisor ajusta su ritmo según las pérdidas que detecta. Protege a la red.

Cierre

Cada sentido se cierra por separado con FIN y ACK. El extremo que cierra primero queda un tiempo en TIME_WAIT, para absorber segmentos atrasados. Esos estados se ven con ss.

4. Protocolos de aplicación

En el modelo cliente-servidor, el servidor espera en un puerto conocido y el cliente inicia la conversación. «Cliente» y «servidor» son roles de procesos, no tipos de máquina.

HTTP

HTTP es texto estructurado (en HTTP/1.1) que viaja sobre TCP. Es sin estado: cada solicitud es independiente, y la sesión se mantiene con cookies o tokens.

GET /cursos/redes?modulo=4 HTTP/1.1          ← método, ruta, versión
Host: www.ejemplo.com                          ← cabeceras
User-Agent: curl/8.5.0
Accept: */*
                                               ← línea vacía: fin de cabeceras
HTTP/1.1 200 OK                                ← versión, código, frase
Content-Type: text/html; charset=utf-8
Content-Length: 5120

<!doctype html>…                             ← cuerpo
MétodoUso
GETobtener un recurso (no debe cambiar nada en el servidor)
POSTenviar datos para procesar o crear
PUT / PATCHreemplazar / modificar un recurso
DELETEborrar un recurso

Los códigos de estado se leen por su primer dígito: 2xx éxito, 3xx redirección, 4xx error del cliente (400, 401, 403, 404), 5xx error del servidor (500, 502, 503). Para quien programa, un 4xx indica que hay que revisar la solicitud y un 5xx, el servidor.

APIs: REST, JSON y sesiones

Buena parte del HTTP que van a programar no devuelve páginas sino datos: es una API REST. Los recursos se nombran con URL, la acción se indica con el método y el resultado con el código de estado. Los datos viajan en JSON.

POST /api/alumnos HTTP/1.1
Host: api.ejemplo.com
Content-Type: application/json

{"nombre": "Ana", "legajo": 42}

HTTP/1.1 201 Created
Location: /api/alumnos/42
Content-Type: application/json

{"id": 42, "nombre": "Ana", "legajo": 42}

Como HTTP no tiene estado, la sesión se mantiene con una cookie (el servidor envía Set-Cookie: sesion=… y el navegador la devuelve en cada solicitud) o con un token en la cabecera Authorization.

Mismo origen y CORS

El navegador aplica la política del mismo origen: el JavaScript de una página solo puede leer respuestas de su mismo origen, que es la combinación de esquema, host y puerto. Si el frontend corre en http://localhost:5173 y la API en http://localhost:8000, son orígenes distintos, y el navegador bloquea la lectura salvo que la API lo autorice con CORS:

Navegador → API   GET /api/estado   Origin: http://localhost:5173
API → Navegador   200 OK            Access-Control-Allow-Origin: http://localhost:5173

Para solicitudes «no simples» (PUT, DELETE, o un POST con JSON), el navegador primero envía un OPTIONS de verificación previa, y solo si la respuesta lo autoriza envía la solicitud real.

Lo que más confunde

El error «bloqueado por CORS» aparece en el navegador, pero se corrige en el servidor. Y casi siempre el servidor sí recibió y respondió la solicitud: lo que bloquea es el navegador, al momento de entregarle la respuesta al script. Por eso con curl «anda»: curl no aplica CORS.

HTTPS, FTP y SSH

  • HTTPS: HTTP dentro de una sesión TLS, en el puerto 443. Lo vemos en el módulo 5.
  • FTP: transferencia de archivos con dos conexiones (control en el 21 y una de datos aparte), sin cifrar. Hoy se prefiere SFTP, que corre sobre SSH.
  • SSH: acceso remoto cifrado a la terminal, en el puerto 22.

5. La red desde el código

Un servidor TCP mínimo en Python 3: espera una conexión en el puerto 5000 y devuelve en mayúsculas lo que recibe. Cada llamada corresponde a algo que ya vimos.

# servidor.py
import socket

with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:   # IPv4 + TCP
    s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    s.bind(("0.0.0.0", 5000))      # todas las interfaces, puerto 5000
    s.listen()                     # estado LISTEN
    print("Escuchando en el puerto 5000")
    conn, addr = s.accept()        # acá termina el handshake
    with conn:
        print("Conexión desde", addr)              # (IP, puerto efímero) del cliente
        while datos := conn.recv(1024):            # recv devuelve b"" cuando el cliente cierra
            conn.sendall(datos.upper())
# cliente.py
import socket

with socket.create_connection(("127.0.0.1", 5000)) as s:   # SYN, SYN-ACK, ACK
    s.sendall(b"hola red\n")
    print(s.recv(1024).decode())
Para pensar

¿Qué cambia si en bind se pone "127.0.0.1" en lugar de "0.0.0.0"? Probalo: desde la misma VM funciona, y desde tu computadora no. Es una de las causas más comunes de «en mi máquina anda».

Wireshark captura lo que pasa por una interfaz y lo decodifica capa por capa. Hay dos clases de filtros, con sintaxis distintas:

Ética

Capturá solo tu tráfico o el de un laboratorio autorizado. Capturar tráfico ajeno sin permiso es una falta grave y puede ser delito. Es la frontera entre diagnóstico y ataque que vamos a retomar en el módulo 5.

Laboratorio 4C · Una API, un frontend y CORS

Ubuntu Server (VM) + navegador60 minutosIndividual

Una API mínima con la biblioteca estándar de Python. Guardala como api.py:

import json
from http.server import BaseHTTPRequestHandler, HTTPServer

PERMITIR = None   # después probá con "http://192.168.56.101:8080"

class API(BaseHTTPRequestHandler):
    def cors(self):
        if PERMITIR:
            self.send_header("Access-Control-Allow-Origin", PERMITIR)
            self.send_header("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
            self.send_header("Access-Control-Allow-Headers", "Content-Type")

    def responder(self, codigo, datos):
        cuerpo = json.dumps(datos).encode()
        self.send_response(codigo)
        self.send_header("Content-Type", "application/json")
        self.cors()
        self.end_headers()
        self.wfile.write(cuerpo)

    def do_OPTIONS(self):                     # verificación previa
        self.send_response(204)
        self.cors()
        self.end_headers()

    def do_GET(self):
        self.responder(200, {"estado": "ok", "origen": self.headers.get("Origin")})

    def do_POST(self):
        largo = int(self.headers.get("Content-Length", 0))
        datos = json.loads(self.rfile.read(largo) or b"{}")
        self.responder(201, {"recibido": datos})

HTTPServer(("0.0.0.0", 8000), API).serve_forever()

Y un frontend mínimo, en ~/front/index.html:

<button onclick="pedir()">GET</button>

9. Autoevaluación

Un servidor web atiende a 500 clientes a la vez en el puerto 443. ¿Cómo distingue cada conexión?

  1. Por la MAC de cada cliente
  2. Por la IP y el puerto de origen de cada cliente
  3. Abre un puerto distinto para cada uno
  4. No puede: atiende de a uno

La conexión es la cuaterna IP y puerto de origen, IP y puerto de destino. Con el destino fijo, el origen diferencia cada conexión.

¿Qué responde un servidor a un SYN dirigido a un puerto donde nada escucha?

  1. SYN-ACK
  2. Nada
  3. RST
  4. FIN

Responde RST, y el cliente informa «conexión rechazada». «Nada» es típico de un firewall que descarta el paquete: el cliente agota el tiempo.

¿Por qué DNS usa UDP para la mayoría de las consultas?

  1. Las consultas son cortas y, si se pierde una, alcanza con repetirla
  2. Porque UDP es más seguro
  3. Porque TCP no permite el puerto 53
  4. Porque UDP cifra los datos

Abrir una conexión TCP para una pregunta de pocos bytes triplicaría la demora. DNS usa TCP cuando la respuesta es grande o para transferir zonas.

El control de flujo de TCP sirve para…

  1. evitar congestionar los routers
  2. cifrar el flujo
  3. elegir la ruta
  4. no desbordar el búfer del receptor

El receptor anuncia su ventana. Lo que protege a la red es el control de congestión.

Una API responde 503. ¿Dónde empezás a buscar?

  1. En la solicitud del cliente
  2. En el servidor: no está disponible o el servicio de atrás no responde
  3. En el DNS
  4. En el cable

5xx es error del lado del servidor; 503 significa servicio no disponible (sobrecarga, mantenimiento, backend caído). Si hubo respuesta HTTP, la red y el DNS funcionaron.

¿Cuál es un filtro de visualización válido en Wireshark?

  1. tcp port 80
  2. host 10.0.0.1
  3. tcp.port == 80
  4. port 80 and tcp

Las otras tres están en sintaxis BPF, que es la de los filtros de captura.

Un servidor hace bind(("127.0.0.1", 8000)). ¿Qué pasa?

  1. Solo acepta conexiones desde la misma máquina
  2. Acepta conexiones desde cualquier red
  3. No puede arrancar
  4. Solo acepta conexiones por UDP

127.0.0.1 es la interfaz de loopback. Para aceptar conexiones de otras máquinas hay que escuchar en 0.0.0.0 o en la IP de la interfaz.

Tu frontend en localhost:5173 no puede leer la respuesta de tu API en localhost:8000, pero con curl funciona. ¿Qué pasa?

  1. Son orígenes distintos y la API no envía Access-Control-Allow-Origin; se corrige en la API
  2. La API está caída
  3. Hay un firewall que bloquea el navegador
  4. El frontend tiene que usar HTTPS

El puerto forma parte del origen. curl no aplica la política del mismo origen; el navegador sí, y la API tiene que autorizar ese origen con CORS.
